# Fixon — SLA Rule Model

## 1. Назначение документа

Документ описывает:
- модель SLA правил,
- принципы их создания,
- структуру условий,
- логику применения правил к отгрузкам и фактам,
- связь правил с контрактами и версиями.

Модель предназначена для:
- формализации договорных обязательств,
- автоматической проверки исполнения SLA,
- прозрачного и воспроизводимого расчёта нарушений.

---

## 2. Ключевые принципы SLA правил

1. SLA правило — это формализованное обязательство
2. Правило привязано к контракту. Расчёты выполняются по версиям (ContractVersion + SlaRuleVersion) согласно `01-domain-model.md` и `02-er-diagram.md`.
3. Правило может применяться не всегда, а при выполнении условий
4. Правило проверяется на основе фактов
5. Результат проверки — нарушение или отсутствие нарушения
6. Правила не хранят бизнес-логику в коде

---

## 3. Связь с контрактами

- Контракт может иметь несколько версий
- Каждая версия контракта содержит свой набор SLA правил
- После активации версия контракта неизменяема
- Новые правила добавляются только через новую версию

Иерархия:
- Contract
- ContractVersion
- SlaRule

---

## 4. Общая структура SLA Rule

SLA Rule состоит из трёх логических частей:

1. Метаданные
2. Условия применимости (When)
3. Условия проверки (Then)

---

## 5. Метаданные SLA Rule

В v1 (см. `01-domain-model.md` / `02-er-diagram.md`) метаданные SLA-правила представлены сущностями `SlaRule` и `SlaRuleVersion`.

`SlaRule`:
- Id
- ContractId
- Name
- IsActive
- CreatedAt

`SlaRuleVersion`:
- Id
- SlaRuleId
- VersionNumber
- EffectiveFrom
- EffectiveTo (nullable)
- CreatedAt
- CreatedByUserId
- IsActive

Метаданные не участвуют в вычислениях, но важны для:
- аудита,
- отчетности,
- UX.

---

## 6. Условия применимости (When)

### 6.1 Назначение

When-условия определяют:
- применяется ли правило к конкретной отгрузке / факту
- нужно ли вообще выполнять проверку

Пример:
- контроль температуры — только для овощей
- контроль акцизных марок — только для алкоголя

---

### 6.2 Структура When-условия

WhenCondition:
- Attribute
- Operator
- Value

Примеры атрибутов:
- cargo.type
- cargo.category
- shipment.mode
- route.country
- vehicle.type

Примеры операторов:
- EQUALS
- NOT_EQUALS
- IN
- NOT_IN

---

### 6.3 Пример When-логики

Правило применяется, если:
- cargo.category = "Vegetables"

ИЛИ

- cargo.category IN ("Vegetables", "Fruits")

Если When-условия не выполнены:
- правило считается NotApplicable
- нарушение не фиксируется

---

## 7. Условия проверки (Then)

### 7.1 Назначение

Then-условия определяют:
- что именно проверяется
- какие значения считаются допустимыми
- при каких условиях возникает нарушение

---

### 7.2 Структура Then-условия

ThenCondition:
- FactKey
- Operator
- ExpectedValue
- Unit (опционально)

Примеры FactKey:
- arrival_time
- waiting_time_minutes
- cargo_temperature
- documents.excise_stamp_present

---

### 7.3 Поддерживаемые операторы

Поддерживаются следующие операторы сравнения:
- EQUALS
- NOT_EQUALS
- GREATER_THAN
- GREATER_OR_EQUALS
- LESS_THAN
- LESS_OR_EQUALS

---

### 7.4 Примеры Then-условий

- waiting_time_minutes LESS_OR_EQUALS 30
- cargo_temperature GREATER_OR_EQUALS 2
- cargo_temperature LESS_OR_EQUALS 6
- documents.excise_stamp_present EQUALS true

---

## 8. Комбинация условий

### 8.1 Логика объединения

- When-условия объединяются через AND
- Then-условия объединяются через AND
- OR не поддерживается в v1 (осознанное ограничение)

---

### 8.2 Интерпретация

Правило считается нарушенным, если:
- все When-условия выполнены
- хотя бы одно Then-условие не выполнено

---

## 9. Версионирование SLA правил

- SLA правило принадлежит конкретной версии контракта
- При создании новой версии:
  - правила копируются
  - могут быть изменены
- Исторические версии не пересчитываются

---

## 10. Результат применения правила

Результат вычисления SLA Rule:
- Passed
- Failed

В v1 `SlaEvaluation.EvaluationResult` фиксируется как `Pass / Fail` (см. `01-domain-model.md`).  
Если When-условия не выполнены, проверка не выполняется и результат можно трактовать как "не применимо" на уровне приложения (например: не создавать запись `SlaEvaluation`).

При Failed создаётся:
- SLA Violation
- основание для Claim

---

## 11. Хранение условий в базе

### 11.1 Подход

- В v1 условия When/Then и описание последствий хранятся в `SlaRuleVersion` как JSON поля:
  - `AppliesWhenJson`
  - `ConditionJson`
  - `PenaltyJson`
  (см. `01-domain-model.md` и `02-er-diagram.md`).
- Нет «динамического кода» и rule-engine фреймворков: правила интерпретируются детерминированно.
- Нет динамического кода

Это позволяет:
- хранить правила прозрачно и воспроизводимо
- версионировать правила

---

## 12. Ограничения v1

- Нет OR внутри условий
- Нет вложенных групп условий
- Нет формул внутри SLA When/Then условий (см. `07-penalties-financial-impact.md` для модели расчёта денежных последствий)
- Нет агрегатов (avg, max, min)
- Один факт = одно значение

---

## 13. Осознанные архитектурные решения

- Простота важнее универсальности
- Явные правила лучше магии
- Ограничения ускоряют запуск
- Модель готова к расширению без переделки

---

## 14. Готовность к реализации

Модель:
- полностью согласована с ER
- подходит для EF Core
- легко сериализуется
- готова к CSV импорту
- не требует rule engine фреймворков
