# Fixon — Authentication & Multi-tenancy

## 1. Назначение документа

Документ описывает:
- модель аутентификации пользователей,
- управление доступом,
- реализацию multi-tenancy,
- ограничения и принципы безопасности.

Модель ориентирована на:
- B2B SaaS
- минимальный технологический стек
- простую и предсказуемую реализацию

---

## 2. Базовые принципы

- Один пользователь принадлежит одной компании
- Все данные всегда фильтруются по CompanyId
- Нет глобальных пользователей
- Нет шаринга данных между компаниями
- Аутентификация отделена от бизнес-логики

---

## 3. Аутентификация

### 3.1 Модель аутентификации

Используется классическая схема:
- Email + Password
- PasswordHash хранится в базе
- Пароли никогда не хранятся в открытом виде

Рекомендуемый алгоритм:
- BCrypt или PBKDF2

---

### 3.2 Процесс входа (Login)

1. Пользователь вводит Email и Password
2. Система:
   - ищет пользователя по Email
   - проверяет IsActive
   - валидирует пароль
3. При успехе создаётся authenticated session

---

### 3.3 Токены

Для v1 рекомендуется:
- JWT (stateless)
- Access Token с коротким TTL
- Refresh Token (опционально)

JWT содержит:
    {
      "userId": "...",
      "tenant_id": "...",
      "roles": ["Admin", "Manager"]
    }

---

## 4. Авторизация

### 4.1 Ролевая модель

Используется простая ролевая модель.

Поддерживаемые роли:
- Admin
- Manager
- Viewer

---

### 4.2 Права доступа (v1)

| Действие | Admin | Manager | Viewer |
|--------|-------|---------|--------|
| Управление пользователями | ✅ | ❌ | ❌ |
| Контракты | ✅ | ✅ | 👁 |
| SLA правила | ✅ | ✅ | 👁 |
| Факты | ✅ | ✅ | 👁 |
| Claims | ✅ | ✅ | 👁 |
| Аудит | ✅ | 👁 | 👁 |

👁 — только просмотр

---

### 4.3 Реализация авторизации

- Проверка ролей на уровне API
- Нет динамических permission
- Нет ACL
- Нет политик доступа по данным (кроме CompanyId)

---

## 5. Multi-tenancy

### 5.1 Модель изоляции

Используется Shared Database, Shared Schema.

Изоляция достигается через:
- обязательный CompanyId
- фильтрацию данных
- проверки на уровне API

---

### 5.2 Правила изоляции данных

- Все tenant-scoped сущности содержат CompanyId  
  (справочные/глобальные сущности без tenant-изоляции — например, `Role` — могут не содержать CompanyId)
- Все запросы фильтруются по CompanyId
- Нельзя указать CompanyId вручную из API
- CompanyId берётся только из auth context

---

### 5.3 Global Query Filter (EF Core)

Пример:
    modelBuilder.Entity<Contract>()
        .HasQueryFilter(x => x.CompanyId == _currentCompanyId);

---

## 6. Контекст пользователя

### UserContext

Во время обработки запроса формируется контекст:
- UserId
- CompanyId
- Roles

UserContext доступен:
- в сервисах
- в audit logging
- в rule evaluation

---

## 7. Аудит действий пользователей

Принципы:
- Все create / update / delete логируются
- Фиксируется:
  - пользователь
  - компания
  - сущность
  - изменения

AuditLog создаётся:
- автоматически
- без участия UI
- на уровне backend

---

## 8. Ограничения v1

- Нет SSO
- Нет OAuth
- Нет MFA
- Нет impersonation
- Нет пользовательских permission

---

## 9. Безопасность (минимальный набор)

- HTTPS only
- Rate limiting (basic)
- Защита от brute-force
- Валидация входных данных

---

## 10. Осознанные решения

- Простая ролевая модель лучше гибкой
- Multi-tenancy важнее масштабируемости
- Явная логика лучше магии
- Ограниченный scope быстрее даёт value

---

## 11. Готовность к реализации

Данная модель:
- полностью согласована с доменной моделью
- подходит для ASP.NET Core
- не требует сторонних identity-фреймворков
- легко расширяется при необходимости
